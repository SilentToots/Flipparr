# SonicBoom Collaboration Principles

## Product stage and delivery target

- SonicBoom is a **pre-release product on a production track**, not a proof of concept, experiment, or disposable prototype. The delivery target is a publicly distributable, installable, self-hosted, single-household Docker release for anyone who wants to run SonicBoom for a NAS-hosted comic library: one admin, and optional reader profiles (amended 2026-09-25; see `docs/RELEASE_TRACK.md`).
- Treat public distribution as a baseline constraint even before the first release. Code, images, fonts, reference data, provider integrations, bundled assets, documentation, container images, and dependencies must have licenses and redistribution terms compatible with that goal. Do not bundle private credentials, authenticated provider exports, or third-party datasets unless their terms explicitly permit the intended distribution and required attribution or notices are implemented.
- Design and implementation decisions must move the product toward the release gates in `docs/RELEASE_TRACK.md`. A feature is not complete merely because it works in the current developer environment or demo UI.
- **Direction (2026-09-03, cleaned up 2026-10-03): one codebase.** The product is built forward from the original application (`app.py`, `catalog_store.py`, `v1-prototype/`) on the `v1-forward` branch. A from-scratch rewrite tried in August 2026 was abandoned and removed from the repository; do not reintroduce a from-scratch rewrite. Harden in place (HTTP-layer migration, module split, targeted safety guards) instead.
- Approved release scope (amended 2026-09-02, carried into V1-forward): a single publication run groups both Issues and collected editions with independent ownership. Issues are the only automatic monitoring, wanted, provider-search and downloader-acquisition target for the first release. **Collected-edition handling is an opt-in feature (default off)** — when on, editions are first-class local-library intake, grouping, metadata, health and manual import/replacement content with a persistent lower-reliability notice; the production UI must never promise missing-volume catalogs or automatic Volume acquisition. Neither format fulfills or depends on the other. Automatic issue-to-volume contents mapping/sync is not a release requirement and must not block volume intake or require manual issue-list entry. Preserve existing evidence and historical Volume request records without using them for cross-format fulfillment.
- V1's general intake, grouping, filename parsing and folder/naming behavior are the product baseline and the codebase base. Changes are made in place through explicit compatibility tests; document intentional differences required by the opt-in-editions scope or a demonstrated safety/correctness defect. Do not add wrong-era matches, duplicate-run behavior or volume-to-issue fulfillment, and do not use exact-edition enrichment as a gate for useful local organization. Rare duplicate runs are a user-fixable "merge runs" action, not a reason to re-architect.
- Experimental spikes are allowed only when they are clearly labeled, isolated, time-bounded, and either discarded or brought through the same tests, migrations, recovery behavior, observability, security, accessibility, documentation, and release review as production code.
- Release work must include clean-install, upgrade, backup/restore, rollback, restart recovery, provider-outage, and realistic-library validation. Silent data reassignment, unexplained background work, and manual database repair are release blockers.
- the NAS Docker is the authoritative runtime and QA environment. Use the local Mac workspace for editing, source inspection, and runtime-independent checks only; run unit/runtime suites, integrations, realistic NAS intake, provider checkpoints, deployment checks, and release-gate evidence on the NAS with `Dockerfile` unless the NAS is genuinely unavailable. Do not repeatedly attempt execution against the Mac's incompatible system Python or treat local-only success as release evidence.

- Challenge assumptions instead of defaulting to agreement. When a proposed direction conflicts with established best practice, creates avoidable risk, or does not fit SonicBoom's stated product goals, explain the concern, its likely impact, and a stronger alternative.
- Keep tradeoffs concrete so the user can make an informed product decision. The user retains final decision authority and may knowingly choose a different tradeoff.
- After the user makes an informed choice, follow that direction unless a safety, authorization, or technical constraint prevents it; in that case, state the constraint plainly.
- Before implementing a significant feature, integration, workflow, data-model change, or architectural decision, research the relevant constraints and established best practices first. Prefer current primary sources such as official documentation, specifications, accessibility standards, and provider policies; do not wait for production or QA failures to discover documented limitations.
- Derive provider limits, quota windows, pacing, retry behavior, timeouts, cache policy, and safety margins from current official documentation and live authoritative response metadata. Record the source, scope, fallback behavior, and verification case with the implementation. Do not substitute arbitrary local limits for documented provider behavior; when a conservative margin is necessary, state and test the concrete reason for it.
- Apply that research across the whole product, not only external integrations. Evaluate maintainable architecture, data integrity and migrations, security and privacy, performance and concurrency, caching and failure recovery, testing and observability, deployment and rollback, accessibility, responsive behavior, design tokens, reusable components, established UX conventions, clear terminology, feedback states, and error recovery as relevant to the work.
- Before building, summarize material findings, risks, and tradeoffs and adjust the implementation approach accordingly. Distinguish an established standard or documented constraint from a product preference, and identify how the behavior will be tested or verified. Keep this proportional: routine low-risk edits do not require unnecessary research, but assumptions with meaningful product, data, operational, or UX impact must be validated.
- Batch small UI polish, spacing, copy, and animation changes into a shared QA deployment instead of rebuilding and deploying the NAS after every individual tweak. Deploy immediately only when a backend or security fix, a blocker, or the next live QA step depends on the change.
- Build the production UI with React, TypeScript/JSX, and Vite. The frontend (`v1-prototype/`) uses a named theme/semantic-token system, reusable components (rather than one monolith), mobile-first and container-responsive layouts, scoped asynchronous states, accessible status messages, and reduced-motion behavior. Verify components across the documented breakpoint, zoom, keyboard, motion, and async-state matrix before considering them complete.
- Styling follows `v1-prototype/DESIGN_SYSTEM.md`: type, spacing, radii, colour and breakpoints come from `src/design-tokens.css`, and `npm test` (in CI) fails on a value that is not a token or a written exception. Before and after any `styles.css` change, run `npm run visual:capture` and `npm run visual:compare` at both viewports and `npm run layout:check`. The Figma file is retired as a reference (2026-09-19); the design system document is the source of truth.
- Apply the UX principles across backend behavior, workflows, content, and presentation rather than treating UX as a visual pass. For every capability, define the user's goal, safe automatic path, minimum decisions, progress/status model, completion evidence, failure recovery, and next action. Do not expose internal data-model or provider mechanics unless they help a user diagnose or recover. Test the full task on realistic data and devices; component conformance alone is not evidence that the experience is understandable or successful.

## End-to-end progress and prioritization

- Continue through safe, already-authorized next steps without treating each progress update as a new approval gate. Report concrete checkpoints and the next action clearly, but pause only for a material user decision, missing access/input, an authorization boundary, or a genuine blocker. This does not authorize unrelated features, deployments, destructive changes, or open-ended background work. Never imply work continues after a turn ends unless a supported ongoing mechanism is actually running.
- Evaluate work against the complete relevant user workflow and its dependencies, not only the component currently being changed. Consider intake, identity, issue/volume coverage, acquisition, validation/import, ongoing healing, and user feedback together when their behavior interacts. This is a whole-product principle, not only a metadata-source strategy.
- Component improvements are valuable foundations, including correctness, maintainability, performance, and recovery work that does not immediately increase coverage. State which user outcome or release risk each improvement addresses, set a bounded checkpoint, and reassess the integrated workflow before extending a narrow line of optimization. Do not let component hardening displace progress toward the complete release toolset or require one subsystem to be perfect before evaluating complementary approaches.
- Before a significant migration or intake change, record the existing behavior and representative input/output baseline, identify every evidence source consumed or omitted, and add executable compatibility cases for the behavior being replaced. At minimum, intake cases must include filename-only files, embedded-only files, conflicting filename/embedded evidence, missing provider references, issues and collected volumes, and same-title different-era negatives. A missing input path is a regression to investigate, not proof that a source lacks data. Passing component tests cannot substitute for this compatibility check.
- Each intake checkpoint must separately report input inventory/health, discovery eligibility, correctly grouped run/format/number, accepted ownership, and required user intervention against the same stated cohort. Label unmeasured stages explicitly. Before extending a narrow optimization for another checkpoint, compare its workflow result with the baseline; if results are flat, surface that fact and reassess omitted inputs and working V1 behavior before further tuning. Do not move the success criterion or equate query readiness with a correct match.
- Prioritize from representative end-to-end evidence: correct unattended resolutions, reduced manual intervention, safe acquisition/import, understandable recovery, and realistic operating costs. Test counts and isolated extraction or matching gains are supporting engineering evidence, not substitutes for demonstrated user benefit. Report foundational progress separately from measured workflow gains and identify what remains untested.
- Use the actual NAS library as the primary intake baseline, with read-only source access and a clean isolated database. Deliberately difficult selected files are regression cases, not representative library coverage. Compare useful organization (correct run, issue/volume identification and visible ownership) separately from exact provider-edition enrichment and optional metadata completeness. Compare against the original build's usable behavior without inheriting or assuming the correctness of its canonical catalog state.
- Filenames are first-class intake evidence and must never be discarded because embedded metadata, OCR or provider records exist. Retain the original filename and independently sourced parsed clues, including title, issue/volume number and distinct run-year/publication-year hints. Reconcile evidence rather than silently overwriting it; disagreements require explicit handling. Missing provider confirmation must not erase useful local clues. Filename conventions alone are not permission to merge same-title runs, credit ownership across formats, or bypass file validation.
- Escalate noticeable collection-resolution plateaus promptly to the user; do not wait for another implementation or test cycle to report them. State the current unattended outcome, denominator, validation limits, and the specific evidence or capability blocking progress. When successive changes yield no workflow gain, stop extending that narrow approach and set a bounded feasibility checkpoint across the available sources. Further experiments need a concrete hypothesis and a stop/change-course criterion. Correctness tests remain necessary for code changes, but passing more tests is not evidence that collection coverage is improving. A material product pivot remains the user's decision.
- Evaluate complementary data sources together, with their documented constraints and evidence strengths. For intake, include embedded metadata, GCD, Metron, Comic Vine, and book/OCR evidence as applicable; do not treat one source as the entire pipeline or missing cached data as proof that data is unavailable. Distinguish evidence not retrieved, not understood, conflicting, and genuinely unavailable after the evaluated searches.
- Use repeatable cohorts to compare integrated outcomes and identify the next bottleneck. Retain separate untouched validation cases as development cases become regressions. Prefer shared fixes over title-specific exceptions, and never weaken identity, coverage, or file-safety safeguards merely to improve an automation metric. Considering the whole workflow does not authorize unrelated feature expansion beyond the agreed release priorities.
